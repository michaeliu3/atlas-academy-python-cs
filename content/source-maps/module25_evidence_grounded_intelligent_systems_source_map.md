## Executive teaching decision

An intelligent feature is often introduced backwards: select a model, report
one metric, show a polished suggestion, then assume it helped. That sequence
erases the critical distinctions among a score, a probability, a prediction, a
recommendation, a decision, an explanation, and an authorization.

Module 25 instead carries one connected chain from earlier Atlas work:

~~~text
user need + harm / non-goal + accountable decision owner
    → authorized minimal event/data contract + candidate set
    → transparent baseline and optional bounded model/policy
    → time-appropriate split + declared target/metric/uncertainty
    → readable ranking and provenance trace
    → accessible explanation + meaningful dismiss / override
    → policy-enforced action boundary + explicit human approval
    → evidence card: benefit, limitations, privacy, accessibility, cost, risks
~~~

### M24 evidence thread → M31–M36 synthesis gate → M25 → M26

The following table compares connected **evidence roles**, not next/previous
navigation. M24 contributes runtime-evidence discipline; the M31–M36 chain
supplies the advanced mathematical, systems, AI/ML, and learning-theory
evidence before M25's synthesis; M26 follows only after M25's own gate.

| Boundary | Module 24 gives the learner | Module 25 adds after M31–M36 | Module 26 must defend |
|---|---|---|---|
| Claim | A benchmark result needs an exact workload and observation layer. | A model metric needs a target, split, population/time scope, decision context, and limitation. | Each release claim is connected to an owner, contract, test or observation, and known limit. |
| Evidence | A timer, profile, allocation trace, and OS metric measure different things. | Offline score, calibration check, slice, accessibility test, user observation, and risk review measure different things. | The capstone does not collapse those layers into a green CI badge. |
| Architecture | A runtime or native boundary changes cost and failure assumptions. | Candidate generation, ranker/model, policy, interface, and tool/authority boundaries are distinct components. | The architecture packet traces data, trust, failure, recovery, and release boundaries. |
| Human effect | Faster code is not automatically a better system. | A high offline score is not automatically a helpful, understandable, accessible, fair, or safe suggestion. | Evidence must cover people and operations as well as code. |
| AI assistance | An agent's optimization explanation is a hypothesis until checked. | LLM/agent output is a proposal, not truth, provenance, permission, or an action. | Agent-generated changes remain untrusted proposals until reviewed and independently verified. |

### Required Atlas checkpoint invariant

> **Atlas may present a versioned, purpose-scoped suggestion only from
> authorized minimal data, a declared candidate set, and a named policy or
> model. Every suggestion preserves provenance, policy/model version,
> evaluation scope, uncertainty or limitation, and an accessible explanation.
> It provides a meaningful dismiss or override path. A score never silently
> changes learner state, grants authority, proves truth, establishes causality,
> or turns user feedback into ground truth.**

This is an **Atlas teaching contract**, not a claim that a small local model is
accurate, calibrated, unbiased, privacy-preserving, accessible in every
assistive-technology combination, legally compliant, secure against every
attack, or suitable for a consequential decision.

## Scope ownership and hard boundaries

### Module 25 owns

- deriving a decision contract before selecting a model: task, users,
  stakeholders, non-goals, baseline, harm, authority owner, success evidence,
  and rollback condition;
- separating event, feature, label/outcome, candidate, score, probability,
  rank, recommendation, policy, decision, explanation, provenance, and
  feedback;
- data provenance, purpose limitation, minimisation, consent/authorization
  context, retention/deletion intent, synthetic fixtures, and ownership of the
  data contract;
- leakage diagnosis, especially information unavailable at prediction time,
  preprocessing fit on the wrong split, feedback/selection contamination, and
  temporally impossible features;
- a transparent deterministic baseline and a deliberately small optional
  learned alternative, each with a readable candidate/ranking trace;
- evaluation contracts: target definition, split strategy, denominators,
  class imbalance, ranking versus classification metrics, calibration,
  thresholds, slices, uncertainty/limits, distribution-shift hypothesis, and
  M24 cost record;
- the distinction between calibrated probabilities and arbitrary scores or
  confidence-like UI labels;
- human-centered decision support: explanation scope, visible uncertainty,
  correction, dismissal, override, feedback semantics, accessibility, and
  usability evaluation;
- bounded LLM/RAG/agent design: context and retrieval provenance, redaction,
  model output as proposal, capability/tool allowlist, independent policy
  enforcement, explicit approval, audit record, and refusal/fallback; and
- an evidence card that makes intended use, test context, benefit evidence,
  limitations, risk, privacy, accessibility, cost, and review owner visible.

### Module 25 mentions but does not teach deeply

- statistical learning theory, causal inference, Bayesian decision theory,
  optimization, generalized linear models, neural-network training, deep
  uncertainty quantification, ranking learning objectives, bandits, online A/B
  experimentation, counterfactual logging, fairness definitions, formal HCI
  research, advanced screen-reader testing, adversarial ML, and legal/privacy
  compliance;
- production feature stores, data warehouses, annotation operations, model
  registries, experiment trackers, distributed model serving, vector databases,
  model gateways, agent orchestration, OAuth implementation, policy engines,
  formal authorization, and red-team operations; and
- third-party models, retrieval systems, and tool protocols only as bounded
  architecture readings—not as required cloud integrations.

### Deferred or explicitly out of scope

- **Module 26:** product release, operations, maintenance, threat-model
  evidence, deployment/rollback, public contribution, and oral architecture
  defense.
- **Later specialist study:** machine-learning theory, recommender systems,
  causal/experimental design, AI safety/security, accessibility engineering,
  privacy engineering, UX research, MLOps, governance, and domain-specific
  high-stakes AI.
- **Never a default exercise:** ingesting personal learning histories,
  predicting a learner's worth or ability, optimizing engagement as a proxy
  for benefit, making a consequential decision, impersonating a user,
  connecting an LLM to arbitrary tools, sending prompts/data to an external
  provider, granting a model credentials, or allowing a score to write system
  state without an independent policy and explicit human approval.

### Required non-claims

Every learner-facing artifact, TA response, visual, model comment, and
agent-generated patch must reject the following:

- “A score is a probability because it is between zero and one.” A probability
  interpretation needs a declared outcome/population/time scope and calibration
  evidence; many scores are only ordering signals.
- “A model is useful because accuracy, AUC, NDCG, loss, or one benchmark rose.”
  A metric measures its declared target and test setup, not user benefit,
  causality, accessibility, safety, fairness, or business value by itself.
- “A random train/test split always validates a future-facing feature.” Split
  design must match the data-generating and deployment question; a feature
  unavailable at decision time is leakage even if the code passes a splitter.
- “Cross-validation makes a leaked target, label, population, or preprocessing
  choice valid.” It can still evaluate the wrong question.
- “An explanation proves a model's reason, causal effect, correctness, or
  fairness.” A UI explanation must name what it actually traces.
- “A click, completion, dismissal, or silence is ground truth.” Feedback has
  a separately defined meaning, exposure process, selection effect, and
  authorization/retention boundary.
- “A calibration plot makes the system certain, safe, or calibrated for every
  subgroup and future distribution.” It is a finite, scoped evaluation.
- “A model card, datasheet, risk checklist, or accessible-looking interface
  certifies trustworthiness.” These are evidence/reporting aids, not proofs or
  certifications.
- “Color, a chart, a tooltip, or a mouse-only control is an accessible
  explanation.” Keyboard operation, semantics, names, text alternatives,
  contrast, focus, and appropriate testing remain required.
- “A retrieved citation validates an LLM claim.” Sources, applicability,
  version, quotation, and conclusion must be independently read and checked.
- “An LLM/tool call owns authorization because a prompt asked it to act.” The
  enclosing policy/authorization system and explicitly authorized human own
  the permission decision.
- “Prompt text, RAG context, tool descriptions, tool output, model output, or
  agent memory is trustworthy by default.” Each is untrusted input until a
  named boundary validates or constrains its use.

## First-principles vocabulary and evidence taxonomy

### The seven distinctions that prevent category errors

| Term | Atlas meaning | Minimum evidence before a strong claim | It does **not** mean |
|---|---|---|---|
| **Event** | A versioned record that something was observed or entered, with source/time/purpose context. | Provenance and collection contract. | A valid label, a fact about the person, or permission for another use. |
| **Feature** | A permitted representation computed from events available at the named decision time. | Data lineage and split/time check. | A neutral fact, an automatically useful signal, or a future outcome. |
| **Label/outcome** | The operationally defined target used to evaluate a prediction. | Meaning, time window, collection/exposure process, and error caveats. | Ground truth in a metaphysical sense. |
| **Score** | A scalar emitted by a stated function/policy for a stated purpose. | Readable trace and versioned input/policy. | A probability, explanation, recommendation, or authority. |
| **Probability** | A score interpreted as an estimated event frequency/likelihood under a declared distribution and outcome. | Held-out calibration evidence and scope/uncertainty. | Certainty about an individual case or future environment. |
| **Rank/recommendation** | An ordering or proposed next action from a declared candidate set, objective, constraints, and presentation policy. | Candidate/ranking trace plus human-impact and accessibility review. | A command, objective fact, or permission to mutate state. |
| **Decision/action** | A state-changing or consequential choice made by an accountable policy and/or authorized person. | Independent authorization, confirmation/override, audit/recovery path. | A direct consequence of a model output. |

### Claim labels required in visuals, notebooks, and reviews

| Label | Meaning | Example | It does not mean |
|---|---|---|---|
| **[DATA CONTRACT]** | Authorized collection/use/retention representation. | This feature uses only local synthetic events available before the suggestion time. | The data is accurate, representative, lawful everywhere, or useful. |
| **[PIPELINE OBSERVATION]** | Reproducible behavior of a named local implementation. | This version ranks candidate B above A for this fixture. | A general predictive or human-benefit result. |
| **[OFFLINE EVALUATION]** | A metric from a named fixed split, target, metric implementation, and run. | NDCG is higher on this held-out synthetic fixture. | Causal benefit, calibrated probability, or live impact. |
| **[CALIBRATION EVALUATION]** | A probability/reliability observation for a named outcome/data slice. | A held-out reliability diagram shows these bin frequencies. | Individual certainty, fairness, or calibration elsewhere. |
| **[HUMAN-USE EVIDENCE]** | Observation of how a named user/task interacts with the feature. | A participant can dismiss and find the explanation with keyboard navigation. | Population-wide benefit, endorsement, or no harm. |
| **[ACCESSIBILITY CHECK]** | A scoped conformance/assistive-technology observation. | The visible control has a keyboard path and exposed name/state in the tested build. | Universal WCAG conformance or usability for every person. |
| **[RISK / POLICY CONTROL]** | A named constraint enforced outside model text. | Write actions require a separate policy decision and explicit approval. | Protection from every input, attack, or implementation defect. |
| **[COURSE MODEL]** | An intentional simplified instructional representation. | The six-card decision pipeline separates ranker from policy. | A complete production architecture or formal specification. |
| **[HYPOTHESIS]** | A falsifiable explanation or expected benefit. | Visible uncertainty may help a learner decide to override. | A conclusion before relevant evidence. |
| **[UNKNOWN]** | An intentionally unproven fact. | Whether this local ranking helps a diverse future population. | Permission to infer a favorable answer. |

### Evidence-layer matrix

| Question | Appropriate first evidence | Supports a bounded statement | Does not settle |
|---|---|---|---|
| Does the function produce the declared local score/rank? | Deterministic fixture, readable trace, regression/oracle. | This version behaves this way on named inputs. | Predictive validity or user benefit. |
| Was information from after the decision used? | Time/provenance lineage and split inspection. | The reviewed path is/was not temporally available. | Representativeness, causality, or a complete privacy analysis. |
| Is one model better on the declared target? | Held-out or appropriately cross-validated metric with denominator/slice. | Comparison on that target/split/population/time. | Future/live benefit, fairness, or human control. |
| Can a displayed score be called a probability? | Independent calibration set/reliability evidence and stated event definition. | Calibration evidence within its scope. | Truth of an individual forecast, utility, or calibration after shift. |
| Does the ranking put relevant candidates early? | Declared relevance labels and ranking metric such as NDCG. | Ranking quality for those labels and cutoffs. | Benefit, diversity, accessibility, or correct final action. |
| Can a person understand, dismiss, and override it? | Task script, accessible UI inspection, user observation, error/recovery trace. | Result for the tested task/build/persons. | Agreement with the recommendation or broad human impact. |
| Does an LLM proposal have a source? | Exact prompt/context/model/version and independently opened source records. | Traceable provenance information. | Factual correctness, permission, or tool safety. |
| May a proposal trigger a write/tool action? | Independent authorization/policy enforcement plus explicit approval record. | This action met this policy in this context. | That the model was correct or all downstream effects are safe. |

### Required decision-system diagram

The workbook and visual studio should use an original, accessible version of
this architecture—not an externally copied diagram:

~~~text
authorized, minimised local events
        │  [DATA CONTRACT]
        ▼
time-valid features ──► declared candidate generator ──► score/rank policy
        │                         │                            │
        │                         │                            ├──► evaluation card
        │                         │                            │     (split, metric, limits)
        │                         │                            ▼
        │                         └──► readable candidate trace
        ▼
accessible suggestion + source/limitation + dismiss/override
        │  [HUMAN-USE + ACCESSIBILITY]
        ▼
separate authorization / approval policy ──► optional state-changing action
        │  [RISK / POLICY CONTROL]               (never model text alone)
        ▼
redacted, purpose-scoped evidence record + review/rollback path
~~~

The diagram's important lesson is **separation**. Candidate generation,
scoring/ranking, display, feedback, authorization, and state mutation are
different responsibilities. Combining them in an opaque recommendation loop is
an architectural choice that needs extra evidence, not a sign of intelligence.

## Source map: evaluation, calibration, leakage, and ranking

### A. scikit-learn: public API and practical evaluation boundaries

#### A1. Model selection and evaluation

Primary source: [scikit-learn — Model selection and evaluation](https://scikit-learn.org/stable/model_selection.html)

The `stable` documentation route was observed as **scikit-learn 1.9.0** on
2026-07-31. It is a mutable version-family route, not a reproducibility pin;
an executable exercise must separately record its installed package version.

Use this official documentation for:

- the distinction between fitting a model, selecting/tuning it, and evaluating
  it with a named scoring rule;
- cross-validation as a family of split/evaluation procedures, not a universal
  answer to deployment-time causal, temporal, or population questions; and
- selecting a metric consistent with the task and documenting the scoring rule.

Atlas may say:

> A model comparison must name its target, split procedure, scoring rule,
> population/time scope, and what the selected score leaves unmeasured.

Atlas must not say:

> A cross-validation helper, a random splitter, or a higher aggregate score
> proves that a feature will help future learners or justifies changing their
> state.

Teaching use: the visual evaluation panel first exposes the target and
denominator, then reveals the metric. Learners diagnose an attractive but
misaligned metric before using a library call.

#### A2. Leakage and preprocessing

Primary source: [scikit-learn — Common pitfalls and recommended practices](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage)

Supported public-documentation claims:

- Data leakage occurs when information unavailable at prediction time is used
  while building a model.
- Leakage can yield overly optimistic estimates and poorer behavior on novel
  data.
- Test data must not drive model choices; in particular, fitting a
  preprocessing transformation on all data leaks test-set information.
- A pipeline can help apply the appropriate learned transformation to the
  appropriate subset; it is not a guarantee that the chosen features, labels,
  cohort, or time boundary are meaningful.

Module 25 rule:

> Before choosing a library splitter, the learner draws **event time → feature
> availability time → prediction/suggestion time → label/outcome time**. A
> feature after the decision point is rejected as temporal leakage even if a
> random split has no overlapping row IDs.

The time-order rule is an Atlas course model derived from the decision contract
rather than a claim that scikit-learn chooses the correct production time
boundary automatically.

Required leakage cases:

| Case | Why it fails | Smallest repair |
|---|---|---|
| Normalizer is fitted before train/test split. | Held-out distribution influenced a fitted transformation. | Fit only on training folds through a declared pipeline. |
| “Completed next lesson” is included as a feature for predicting the next lesson. | Outcome/future information entered the input. | Remove/re-time the feature; document availability. |
| A learner's later click is treated as a universal relevance label. | Exposure, UI position, and feedback semantics confound what the click means. | Define the label, exposure condition, and alternative non-click outcomes; keep it a hypothesis. |
| Randomly split events from one timeline. | It may put later state into the training view of an earlier decision. | Use an explicitly documented chronological/grouped split if that matches deployment. |

#### A3. Calibration and probability language

Primary source: [scikit-learn — Probability calibration](https://scikit-learn.org/stable/modules/calibration.html)

Supported public-documentation claims:

- A well-calibrated binary classifier is one where predictions close to a
  stated probability correspond approximately to the observed positive
  frequency in that evaluation context.
- Calibration curves/reliability diagrams compare binned predicted
  probabilities with observed frequencies.
- Some models provide poor estimates of class probabilities; a probability
  API name alone does not certify a useful probability interpretation.
- The documentation cautions that Brier and log loss combine calibration,
  discrimination/resolution, and data uncertainty; a lower Brier score alone
  does not necessarily mean better calibration.
- A calibrator should be fitted on data independent from the data used to fit
  the original classifier; using training outputs can bias calibration.
- Isotonic calibration can introduce ties and can change ranking metrics such
  as ROC-AUC; calibration and ranking objectives are related but distinct.

Module 25 rule:

> The interface says **score** unless the evidence card names the event,
> population/time scope, held-out calibration procedure, sample/uncertainty
> limits, and a reason the probability wording is appropriate. Even then it
> shows an estimate, not a promise.

Teaching use: present three UI labels—priority 0.81, 81% likelihood of
completion, and recommended next step—and ask which is defensible from a given
evidence card. The answer often is only the first.

#### A4. Ranking metrics and a baseline

Primary sources:

- [scikit-learn — Model evaluation](https://scikit-learn.org/stable/modules/model_evaluation.html)
- [scikit-learn — NDCG score](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.ndcg_score.html)
- [scikit-learn — DummyClassifier](https://scikit-learn.org/stable/modules/generated/sklearn.dummy.DummyClassifier.html)

Supported use:

- Use a metric only with the relevance/target labels, cutoff, averaging, and
  weighting explicitly visible.
- NDCG is a ranking-quality metric relative to supplied true relevance scores;
  it does not convert relevance labels into a causal user-benefit proof.
- A deliberately simple baseline makes the question “what additional evidence
  did complexity earn?” inspectable. A dummy estimator is a baseline device,
  not an endorsement of a product policy.

Supplementary primary source: Järvelin and Kekäläinen,
[Cumulated Gain-based Evaluation of IR Techniques](https://doi.org/10.1145/582415.582418)
(2002). Use it for the origin and assumptions of gain/discount vocabulary;
keep the workbook's examples original and do not turn a ranking metric into a
universal objective.

### B. Primary research: reporting, data lineage, calibration, and human AI

#### B1. Dataset documentation

Primary source: Gebru et al., [Datasheets for Datasets](https://arxiv.org/abs/1803.09010).

The paper proposes dataset documentation covering motivation, composition,
collection, preprocessing, recommended uses, distribution, and maintenance. It
supports the module's **data card** idea: an event/feature/label artifact needs
a recorded origin and intended-use boundary.

Boundary: Datasheets are a proposed transparency/accountability practice, not
a claim that all data can be made safe, representative, consented, accurate, or
suitable by filling a form. Atlas uses an original, smaller data-card template
suitable for synthetic fixtures; it does not reproduce the paper's template
wholesale.

#### B2. Model and evaluation reporting

Primary source: Mitchell et al.,
[Model Cards for Model Reporting](https://arxiv.org/abs/1810.03993).

The paper proposes structured reporting of model details, intended uses,
evaluation procedures, and relevant performance characteristics. It supports
the Module 25 **evidence card**: attach intended-use, test context,
limitations, and non-goals to a model/policy artifact rather than presenting
one headline metric.

Boundary: A model card is not a compliance certificate, proof of fairness,
guarantee of performance after deployment, or a replacement for testing the
actual surrounding system.

#### B3. Calibration research

Primary source: Guo, Pleiss, Sun, and Weinberger,
[On Calibration of Modern Neural Networks](https://proceedings.mlr.press/v70/guo17a.html)
(ICML 2017).

It frames confidence calibration as probability estimates representative of
observed correctness likelihood and empirically finds modern networks can be
poorly calibrated in its studied settings. Use it as a primary-research bridge
to the official library documentation and to explain why apparent confidence
needs evaluation.

Boundary: Its results, data, architectures, and post-processing findings do
not establish the calibration of Atlas's model, all model classes, or any
future population. Do not present temperature scaling as a universal repair.

#### B4. Human-AI interaction

Primary source: Amershi et al.,
[Guidelines for Human-AI Interaction](https://doi.org/10.1145/3290605.3300233)
(CHI 2019).

The study proposes 18 interaction guidelines and reports multiple evaluation
rounds with design practitioners. It is the pedagogical basis for teaching:

- show what an AI feature can do and make relevant uncertainty visible;
- support correction, feedback, and graceful failure/recovery rather than
  treating the first output as final; and
- evaluate the interaction around the model rather than looking only at a
  detached metric.

Boundary: The guidelines are research-informed design guidance, not an
accessibility standard, a complete safety framework, or evidence that any
specific user interface is helpful. W3C sources below own web accessibility
requirements.

#### B5. System-level ML debt and boundary erosion

Primary source: Sculley et al.,
[Hidden Technical Debt in Machine Learning Systems](https://proceedings.neurips.cc/paper_files/paper/2015/hash/86df7dcfd896fcaf2674f757a2463eba-Abstract.html)
(NeurIPS 2015).

Use this source for the design warning that an ML model sits inside a larger
system and can create coupling, glue code, feedback loops, hidden consumers,
and maintenance costs. It motivates separated contracts and a transparent
baseline before an optional learned component.

Boundary: This is a conceptual/system-design paper, not a quantified proof of
the cost or reliability of the Atlas project or a reason to reject every model.

## Source map: governance, privacy, accessibility, and agent boundaries

### C. NIST: risk, trustworthy characteristics, and authorization architecture

#### C1. AI Risk Management Framework 1.0

Primary source: [NIST AI 100-1 — AI Risk Management Framework 1.0](https://doi.org/10.6028/NIST.AI.100-1)

Supported use:

- NIST presents a voluntary, rights-preserving, non-sector-specific framework
  for managing AI risks through the lifecycle.
- Its trustworthy-AI vocabulary includes valid and reliable; safe; secure and
  resilient; accountable and transparent; explainable and interpretable;
  privacy-enhanced; and fair with harmful biases managed.
- The framework organizes activity around **Govern, Map, Measure, and Manage**.

Module 25 uses this as a review scaffold, not a compliance claim:

| RMF function | Atlas translation |
|---|---|
| Govern | Name the accountable owner, allowed purpose, non-goals, review rule, and change/rollback boundary. |
| Map | Describe users, task, candidates, data lineage, harms, context, and dependencies. |
| Measure | Run scoped technical, calibration, accessibility, and human-use observations; record limits. |
| Manage | Decide whether to retain, change, pause, roll back, or refuse the feature based on the evidence. |

No learner may claim that completing the table makes a system NIST-certified,
trustworthy, fair, safe, compliant, or fit for high-stakes use.

#### C2. Generative-AI profile

Primary source: [NIST AI 600-1 — Generative AI Profile](https://doi.org/10.6028/NIST.AI.600-1)

Use the profile for its definition and risk framing of **confabulation**:
generative systems can produce confidently presented false or internally
inconsistent content, including false logic or citations. Its risk framing
supports the rule that a generated answer, explanation, or citation is not
evidence until independently checked in scope.

The profile also supports treating generative-AI risk management as an
end-to-end system problem rather than a prompt-writing exercise.

Boundary: the profile is voluntary guidance, not a proof that an individual
LLM will confabulate in a particular prompt, a license to use private data, or
a substitute for a specific threat model and validation design.

#### C3. Privacy context

Primary sources: [NIST Privacy Framework 1.0 and current project page](https://www.nist.gov/privacy-framework)
and [Privacy Framework 1.1 Initial Public Draft](https://www.nist.gov/privacy-framework/using-privacy-framework-11)

At the 2026-07-31 recheck, NIST presented Privacy Framework 1.1 as an
**Initial Public Draft**, not a finalized framework. The module uses its
risk-management framing only; it does not claim PF 1.1 final status,
certification, legal compliance, or endorsement.

Use NIST's data-processing-ecosystem framing to explain why a data boundary
does not end at the first model function: collection, processors, external
providers, deployment, logs, retention, and reuse affect privacy risk.

Module 25's practical default is deliberately stricter and simpler: synthetic
local fixtures, purpose-scoped records, field minimisation, no secrets, and no
external model/provider. If a later real-data project is considered, it needs
an explicit legal, consent, retention, and privacy review outside the course.

#### C4. Policy enforcement, not model authority

Primary source: [NIST SP 800-207 — Zero Trust Architecture](https://doi.org/10.6028/NIST.SP.800-207)

The zero-trust model distinguishes a policy decision point from a policy
enforcement point. Module 25 uses that architectural vocabulary in a narrow
way: a model/agent may propose, but a separate policy/authorization boundary
checks whether an action is allowed in this context.

Boundary: SP 800-207 is an enterprise zero-trust architecture document, not an
AI-agent tutorial or an implementation guarantee. Atlas's small policy gate is
a course model, not a production identity-and-access system.

### D. W3C: accessibility as part of the decision contract

#### D1. WCAG 2.2

Primary source: [Web Content Accessibility Guidelines (WCAG) 2.2](https://www.w3.org/TR/WCAG22/)

The module's visual studio and decision card must use WCAG 2.2 as the relevant
web accessibility reference. Particularly useful source cards include:

- **1.1.1 Non-text Content:** diagrams/charts need appropriate text
  alternatives or adjacent textual explanation;
- **1.4.1 Use of Color** and **1.4.3 Contrast (Minimum):** a score, warning,
  positive/negative state, or data point cannot be communicated by color alone
  and text must remain legible;
- **2.1.1 Keyboard:** all functionality must be keyboard-operable unless the
  underlying function truly requires path-dependent input;
- **2.4.7 Focus Visible** and **2.4.11 Focus Not Obscured (Minimum):**
  keyboard users must be able to locate the active control;
- **3.2.2 On Input:** changing a selection or focus must not silently trigger
  a surprise change of context/action;
- **3.3.1 Error Identification** and **3.3.2 Labels or Instructions:** a
  person needs comprehensible correction/recovery support; and
- **4.1.2 Name, Role, Value** and **4.1.3 Status Messages:** interactive
  controls and dynamic result/error states need programmatically determinable
  semantics where the criterion applies.

Course boundary: WCAG conformance has defined scope and methods. Passing a
small manual checklist or one automated audit does not justify a global
conformance claim. The course instead records what was tested, which tool or
assistive-technology path was used, and what remains untested.

#### D2. Accessible explanation patterns

Primary sources:

- [WAI-ARIA Authoring Practices — Disclosure pattern](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/)
- [WAI-ARIA APG — Providing Accessible Names and Descriptions](https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/)
- [WAI-ARIA overview](https://www.w3.org/WAI/standards-guidelines/aria/)

Use these sources to make the “Why this suggestion?” card concrete:

- default to native HTML controls where practical;
- an expandable explanation needs a named, keyboard-operable control with the
  correct exposed expanded state;
- interactive controls need short, useful accessible names; visible text is
  preferable when it can serve that role; and
- a live update/result needs a readable, testable textual state rather than an
  animation or color change alone.

Boundary: ARIA attributes do not repair a confusing purpose, bad label,
unreadable explanation, unjustified score, or harmful recommendation. A code
snippet is not a claim that every screen reader/browser combination behaves
identically.

### E. LLM and tool/agent boundaries

#### E1. Model Context Protocol as a concrete protocol reading

Primary source (dated specification):
[Model Context Protocol specification — 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25)
and [Authorization — 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)

The specification is not an Atlas dependency or conformance claim. It is a
useful dated example of explicit boundaries:

- tool descriptions/annotations are not intrinsically trustworthy;
- tools can represent arbitrary code execution and need caution;
- consent, data exposure, user approval, and access controls are
  responsibilities of the host/application around the protocol; and
- authorization is a distinct transport/resource concern with audience/scoping
  considerations.

Module 25's portable lesson is therefore not “use MCP.” It is:

> Treat context, retrieval, tool metadata, and model output as data crossing a
> boundary. The application exposes only allowed capability, validates the
> request/result, requires explicit approval for consequential actions, and
> records the policy/version/provenance needed to review the result.

Boundary: protocol conformance does not demonstrate that a tool is harmless,
that authorization is correctly implemented, that content is true, or that a
user intended a downstream effect. The specification evolves; use the dated
version in a source card and re-review it before implementing an integration.

#### E2. Threat vocabulary, kept secondary

Supplementary source: [OWASP Top 10 for Large Language Model Applications —
v2025](https://owasp.org/www-project-top-10-for-large-language-model-applications/assets/PDF/OWASP-Top-10-for-LLMs-v2025.pdf)

Use this living community resource only for threat-review vocabulary—prompt
injection, insecure output handling, sensitive-information disclosure,
excessive agency, and overreliance. It illustrates why an LLM must not be its
own permission system.

Boundary: OWASP's v2025 document is a dated, changing community resource, not
a primary law, formal standard, or a complete threat model. It was rechecked on
2026-07-31; do not claim compliance, security, or immunity from its list.

#### E3. Required Atlas agent boundary

The default Module 25 feature requires no LLM. If an optional hypothetical
adapter is drawn, it must satisfy all of the following on paper and in code:

| Boundary | Required teaching control | What it prevents the course from claiming |
|---|---|---|
| Context | Fixed, redacted, purpose-scoped synthetic context; context ledger. | “The model saw everything relevant” or “it knows the learner.” |
| Retrieval | Source ID/version/snippet boundary and independent source review. | “A citation proves the generated conclusion.” |
| Output | Structured proposal schema with validation/error path. | “Natural language is a safe command or a fact.” |
| Capability | Allowlisted, least-capable interface; default read-only/no external tool. | “The agent can take whatever helpful action it imagines.” |
| Authority | Separate policy enforcement and explicit human confirmation before state change. | “The model decided, therefore it is authorized.” |
| Memory/logs | Redacted, bounded, retention-defined evidence record; no hidden durable memory. | “Conversation history is harmless telemetry.” |
| Fallback | System remains useful with no model/no tool; show refusal or manual route. | “The AI dependency is necessary to provide the service.” |

## Session-level source and artifact route

### Session 25.1 — Purpose before prediction

**Question:** What human problem and decision boundary exist before a model?

- Retrieve M4 probability/logic, M5 measurement, M11 objectives/ranking, M13
  contracts/tests, and M22 authorization/privacy.
- Read the NIST AI RMF function names after the learner writes an original
  decision contract. Treat them as a review vocabulary, not a fill-in-the-box
  compliance exercise.
- Create: a decision contract with user need, counterfactual baseline,
  non-goals, harm/failure costs, accountable action owner, and rollback
  condition.

**Source card:** NIST AI 100-1.  
**Prediction prompt:** “If a ranker predicts a next step accurately, who is
allowed to change the learner's schedule?”  
**Required answer:** model output is not the permission boundary.

### Session 25.2 — Data becomes a claim

**Question:** How does an event become a feature/label without importing the
future or silently changing purpose?

- Read scikit-learn leakage guidance after drawing the four time points.
- Read the Datasheets proposal as a documentation pattern; make a compact
  original data card for synthetic fixtures.
- Create: data-lineage diagram and split ledger showing availability, feature
  transformation ownership, label definition, and excluded fields.

**Source cards:** scikit-learn Common Pitfalls; Gebru et al.; NIST Privacy
Framework.  
**Prediction prompt:** “What information is present in this feature at the
time the user needs a suggestion?”  
**Required answer:** distinguish observation time from use/decision time.

### Session 25.3 — Candidates, rankers, models, and policy

**Question:** How does a transparent score differ from a learned prediction
and from a final action policy?

- Reuse M8–10 candidate/index/graph reasoning and M11 objectives/ranking.
- Hand-trace one deterministic candidate generator and transparent baseline.
- Compare an optional small learned alternative only if it has a versioned
  local fixture and equivalent candidate set.
- Create: candidate trace, policy card, and a baseline-versus-model ledger.

**Source cards:** scikit-learn model evaluation/DummyClassifier; Järvelin and
Kekäläinen; Sculley et al.  
**Prediction prompt:** “Which component decides whether candidate A is shown,
and which component decides whether it may change state?”  
**Required answer:** presentation/ranking and authorization are separate.

### Session 25.4 — Evaluation under uncertainty

**Question:** What does the metric measure, and what does it leave unknown?

- Start with label definition, split ledger, denominator, class/relevance
  distribution, and transparent baseline.
- Compare classification/ranking/calibration quantities without mixing them.
- Surface threshold and slice tradeoffs, sample/shift limits, and M24 runtime
  cost.
- Create: evaluation card with raw fixture results, metric definitions,
  reliability view, limitation, and next falsifier.

**Source cards:** scikit-learn Model Evaluation and Calibration; Guo et al.  
**Prediction prompt:** “Does 0.81 mean high priority, 81% likelihood, or a
recommendation?”  
**Required answer:** only what the evidence/card permits.

### Session 25.5 — Human control and accessible explanation

**Question:** Can a person understand the limited proposal, reject it, correct
it, and operate it without a mouse or color-only signal?

- Build an original “Why this suggestion?” disclosure with visible limitation,
  candidate provenance, keyboard action, focus, accessible name/state, and
  clear dismiss/override behavior.
- Test the task/script before declaring the UI legible.
- Create: accessible decision card and a brief human-use/accessibility
  observation sheet.

**Source cards:** WCAG 2.2; WAI-ARIA APG; Amershi et al.  
**Prediction prompt:** “If keyboard users can reach the score but cannot
discover the explanation or dismissal, what part of the decision contract is
broken?”  
**Required answer:** meaningful human control/accessibility, not just styling.

### Session 25.6 — LLM/agent boundary and release review

**Question:** What can a generative component propose, and what must stay
outside its authority?

- Treat any LLM result as a structured, redacted proposal with exact
  prompt/context/model/version provenance and independent verification.
- Draw tool/capability, policy, consent/approval, and fallback boundaries.
- Create: agent capability ledger, rejected-action test, and evidence-card
  release decision.

**Source cards:** NIST AI 600-1; MCP dated specification; NIST SP 800-207;
OWASP threat vocabulary (secondary).  
**Prediction prompt:** “What changes if a tool result contains an instruction
to call another tool?”  
**Required answer:** it remains untrusted input; the separate policy gate and
explicit approval own the action decision.

## Visual-studio and assessment authoring brief

### Required visual views

The HTML studio should use original diagrams, visible focus, keyboard-reachable
controls, high-contrast text, reduced-motion support, text equivalents, and a
predict → confidence → reveal interaction. It must not invoke a live model,
execute user source, call a tool, collect telemetry, or persist sensitive
personal data.

1. **Decision pipeline** — Purpose → data → candidates → score/rank → human
   card → policy/approval → evidence record. Learner labels the first
   component allowed to change state.
2. **Time and leakage inspector** — Event, availability, decision, and label
   timelines. Learner finds features that travel backward from the future.
3. **Candidate/ranking trace** — Three synthetic actions, transparent baseline,
   optional small model, tie/threshold policy, and source/version cards.
4. **Metric and calibration panel** — Denominator, class/relevance balance,
   held-out split, ranking comparison, reliability diagram, limitations, and
   M24 cost scope—never a generic green “AI quality” meter.
5. **Accessible decision card** — Plain-language why/why-not, limitation,
   keyboard-operable disclosure, dismiss, override, correction, and status
   state.
6. **Agent/tool boundary map** — Redacted context → proposal → validation →
   capability/policy gate → explicit approval; retrieval/tool output crosses
   in as untrusted input.

### Confidence-aware multiple-choice diagnostics

Each question has one best answer, a confidence selection, and feedback that
names the relevant evidence layer. High-confidence misses route back to a
source card and an explanatory counterexample—not a larger coding drill.

| Prompt | Best understanding demonstrated | Misconception rejected |
|---|---|---|
| A feature contains an event recorded after the recommendation time. What is the first problem? | It is temporal leakage unless the decision contract says the information was available then. | “A random split makes timing irrelevant.” |
| A ranker has 90% accuracy. What must be known before calling it useful? | Target, denominator/class balance, baseline, split, failure cost, and human decision context. | “One high metric proves value.” |
| A model emits 0.81. When may the UI call it an 81% probability? | Only with a defined event/population/time scope and suitable held-out calibration evidence. | “All bounded scores are probabilities.” |
| A calibration curve improves while ranking ties change. What follows? | Calibration and ranking objectives are distinct; inspect the declared metric and use case. | “Calibrating always preserves every ranking metric.” |
| Why is a user click not automatically a label? | It may reflect exposure, position, friction, intent, or UI design; its meaning must be defined. | “Observed behavior is ground truth.” |
| A “Why?” explanation works with a mouse but has no keyboard path. Which claim fails? | The accessible human-control contract is unproven. | “Text next to a score makes it accessible.” |
| A retrieved page tells the agent to call a tool. Which boundary decides? | The separate capability/policy/approval path, not the retrieved text or model. | “The agent should follow context instructions.” |
| A fast local agent demo produced useful prose. What is still missing? | Provenance, output validation, allowed capability, approval, privacy, risk, and human-impact evidence. | “A successful demo is a deployable system.” |

### TA and study-partner protocol

| Moment | Instructor | TA | Study Partner |
|---|---|---|---|
| Before model choice | Reconstructs the decision contract and counterfactual baseline. | Asks who owns action authority and what outcome/harm is named. | Restates the difference between score, recommendation, and decision in plain language. |
| During data review | Keeps source/time/purpose/retention boundary visible. | Asks “could this exist at decision time?” and “what does this label actually mean?” | Draws the event → feature → suggestion → outcome path and searches for future leakage. |
| During evaluation | Names the split, target, denominator, metric, calibration scope, and limitation. | Requests a competing metric/slice and a next falsifier. | Challenges a jump from offline score to human benefit. |
| During UI review | Requires explanation, dismiss/override, keyboard path, semantic states, and error/fallback. | Tests focus/order/name/state and asks what a user can do when they disagree. | Plays the user who needs to reject, correct, or understand uncertainty. |
| During agent review | Separates model output from authorization/policy. | Requests the capability ledger, redaction boundary, and rejected-action evidence. | Treats all retrieved/model/tool text as untrusted and asks “who actually approved this?” |
| At handoff | Grades evidence quality and limitation language. | Identifies the smallest missing evidence item. | Helps prepare the oral explanation without overclaiming. |

TA repair prompts:

- If the learner says “the score is 0.9, so it is 90% likely,” ask for the
  event definition, held-out calibration set, population/time scope, and
  displayed uncertainty.
- If they say “we used cross-validation, so there is no leakage,” ask when
  each feature became available, what was fitted, and whether split logic
  matches the deployment question.
- If they say “NDCG improved, so learners benefit,” ask who supplied relevance
  labels, which cutoff matters, what user task was observed, and what could
  still be harmed.
- If they say “the user clicked it, so it worked,” ask whether it was shown,
  what the click means, what counterfactual exposure exists, and whether the
  user could dismiss or correct it.
- If they say “the LLM cited a source,” ask them to open the source, verify its
  date/scope/claim, and distinguish citation provenance from truth.
- If they say “the agent has access,” ask which tool, field, recipient,
  policy gate, explicit approval, retention rule, and rollback path exist.

## Workbook-author acceptance checklist

### Conceptual coherence

- [ ] The workbook begins with a human need, non-goal, baseline, and authority
  boundary before any model/library/API discussion.
- [ ] Every session returns to the same Next-Step Evidence Studio scenario;
  no detached classification or LLM demo replaces the system story.
- [ ] M4/M5 probability and measurement, M8–11 candidate/ranking/objective,
  M12–16 contracts/tests/data/transactions, M20–22 trust/privacy, M23
  semantics, and M24 performance evidence are explicitly retrieved.
- [ ] Score, probability, prediction, rank, recommendation, decision,
  explanation, feedback, and authorization stay visually and verbally
  distinct.
- [ ] The M26 handoff describes a versioned evidence bundle and oral defense,
  not a last-minute coding marathon.

### Source and evaluation integrity

- [ ] Every library claim records exact package/version if a runnable artifact
  uses it; no stable page is treated as a timeless pin.
- [ ] Every metric includes target, split, denominator, cutoff/threshold as
  applicable, baseline, data/version scope, and nearby limitation.
- [ ] Feature availability is checked before split/model code; preprocessing is
  fit only on allowed training data.
- [ ] A calibration claim names the event, held-out procedure, population/time
  scope, and the fact that a finite reliability view is not individual
  certainty.
- [ ] Ranking, calibration, classification, user experience, accessibility,
  privacy, and runtime cost are never collapsed into a generic quality score.
- [ ] At least one counterexample and next falsifier accompany each important
  conclusion.

### Human control, accessibility, and agent safety

- [ ] Every suggestion exposes a plain-language purpose, provenance/why,
  limitation, dismiss/override/correction route, and no-surprise behavior.
- [ ] Every visual control has a keyboard path, visible focus, useful name,
  exposed state where needed, and text alternative/description appropriate to
  its role; color is not the sole carrier of meaning.
- [ ] Any accessibility claim states its tested build/task/tool boundary; it
  does not overstate full conformance.
- [ ] Any LLM/agent is optional, fixed-context/redacted, proposal-only, and
  remains useful when absent.
- [ ] Context, retrieval, tool metadata, tool output, model output, and memory
  are all treated as untrusted inputs until constrained/validated.
- [ ] Capability is minimum and allowlisted; policy enforcement and explicit
  human approval are outside the model; rejected actions have a test.
- [ ] No external model endpoint, personal records, secrets, telemetry, or
  automatic state mutation enters the default artifact.

### Assessment and production quality

- [ ] Diagnostics use multiple choice plus confidence and assess reasoning
  about boundaries, evidence scope, and architecture—not API memorization.
- [ ] TA/Study Partner prompts first elicit a prediction, then ask for the
  evidence layer and the smallest next check.
- [ ] The reference model is deterministic, small, local, and independently
  testable; a baseline remains readable without model-library magic.
- [ ] All charts, examples, fixtures, questions, and diagrams are original and
  synthetic; source links and license notes remain nearby.

  unknowns/rollback rather than a security-clean or human-benefit conclusion.

## Final research verdict

Module 25 can be advanced without becoming an opaque tour of current AI tools.
The foundational reasoning chain is:

~~~text
purpose + non-goal + accountable authority
    + authorized/time-valid data and a declared candidate set
    + transparent baseline or bounded model/policy
    + split-appropriate, metric-specific, calibrated-when-needed evidence
    + accessible explanation, dismissal, correction, and human control
    + separate policy enforcement for any action
    + provenance, limitation, risk, and next falsifier
    = a reviewable decision-support claim
~~~

That standard carries forward the learner's first-principles philosophy in the
AI era: models and agents are components to read, test, constrain, explain,
and sometimes reject—not authorities that turn output into truth or action.
